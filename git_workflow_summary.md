# Git Workflow для проекта SFMShop

## Использованные команды Git
- `git init` — инициализация репозитория
- `git add .` — добавление всех изменённых файлов в staging area
- `git commit -m "message"` — создание коммита с сообщением
- `git status` — просмотр текущего состояния репозитория
- `git log --oneline --graph --all` — визуализация истории коммитов
- `git log --stat` — статистика изменений по файлам
- `git branch -a` — список всех веток (локальных и удалённых)
- `git checkout -b <branch>` — создание и переключение на новую ветку
- `git checkout <branch>` — переключение на существующую ветку
- `git merge <branch>` — слияние ветки с текущей
- `git rebase <branch>` — перенос коммитов поверх другой ветки
- `git push -u origin <branch>` — отправка ветки в удалённый репозиторий
- `git pull` — получение изменений из удалённого репозитория
- `git stash` — временное сохранение незакоммиченных изменений
- `git stash pop` — восстановление спрятанных изменений
- `git diff <branch1> <branch2>` — сравнение двух веток
- `git show <commit>` — просмотр содержимого конкретного коммита

## Созданные ветки
- `main` — основная ветка проекта (стабильная версия)
- `feature/add-discount-system` — система скидок в классе Product
- `feature/add-email-validation` — валидация email в классе User
- `feature/add-inventory-management` — управление складом (check_stock, update_stock)
- `feature/add-shipping` — расчёт доставки (calculate_shipping)
- `feature/test-conflict` — ветка для обучения разрешению конфликтов
- `feature/test-rebase` — ветка для обучения rebase
- `feature/add-logging` — система логирования
- `feature/add-caching` — система кэширования

## Разрешённые конфликты
- **Конфликт в `src/models/product.py`** при слиянии `feature/add-discount-system` и `main` — разрешён объединением методов.
- **Конфликт в `src/models/product.py`** при слиянии `feature/add-shipping` и `main` — разрешён объединением методов `calculate_shipping` и `get_category`.

## Стратегия работы с ветками
1. Основная ветка — `main` (всегда стабильна)
2. Новая функциональность разрабатывается в отдельных ветках `feature/xxx`
3. Перед началом работы ветка обновляется из `main` через `git rebase` или `git merge`
4. После завершения работы создаётся Pull Request в `main`
5. PR проверяется, при необходимости разрешаются конфликты
6. После успешного слияния feature-ветка удаляется

## Стратегия работы для команды
- **main** — запрещены прямые коммиты, только через PR
- **feature/*** — ветки для новых задач
- **hotfix/*** — ветки для срочных исправлений (создаются от main)
- Каждый PR должен быть проверен хотя бы одним участником команды
- Коммиты должны иметь осмысленные сообщения на русском или английском
